# 划词无响应排查与修复（1.0.1）

## 当前证据

- 用户反馈选中英文没有「译」图标。
- GUI 应用持续显示未取得辅助功能授权；系统设置同名 HyperTranslate 开关为开启，重启应用后仍不一致。
- 实际运行路径为本项目 `dist/HyperTranslate.app`，不是另一个应用目录中的副本。
- 本地使用 ad-hoc 签名，开发过程中重新打包会改变 cdhash。旧授权对应旧签名是可能原因，尚未读取系统授权数据库，因此不能将其写成已证实的唯一原因。
- 另外确认代码会在任意主浮窗可见时拒绝显示图标，而输入页、设置页及准备页切换到其他应用后不会自动关闭。这会导致权限正常时也无法从这些页面继续划词。

## 修改

- 去掉主浮窗可见就禁止显示图标的限制；保留系统语言包准备期间的保护。
- 每次启动都显示页面；缺少辅助功能授权时优先打开准备页。重新打开应用也会重新读取权限，避免只显示菜单栏让用户以为没有启动。
- 将本次应用版本标为 1.0.1（build 2），补充旧授权失效的操作说明。

## 验证边界

本次重新打包改变了本地签名。1.0.1 经重新授权后，用户曾确认图标与翻译均正常，随后再次反馈 Chrome 没有图标。因此此前一次通过只能证明当次操作有效，不能作为问题已彻底解决的依据。命令行的权限状态不能替代 GUI 授权及实际操作验证。

- 现有 19 项定向测试全部通过，Debug、Release 编译通过，正式包签名严格验证通过。
- 已实机确认 1.0.1 启动后直接显示权限准备页，不再只有菜单栏无窗口；当前系统语言包检查为已安装。
- 用户重新开启开关并重启后，1.0.1 仍显示未授权。移除旧项目、重新添加当前应用并开启后，GUI 已显示正常输入页，且不再出现缺少授权的提示，确认当前应用已识别权限。macOS 27 上该权限页面实际名称为「设备控制和数据访问」。
- 用户按浏览器划词及点击翻译的验收步骤反馈“图标和翻译都正常”，确认本次使用场景通过。用户未提供浏览器名称，此结论不扩展为 Safari、Chrome、Preview 或 VS Code 全部已验收。重新授权后没有重新打包或更改应用签名。

## 再次无响应：1.0.2

### 证据与边界

- 用户明确本次发生在 Chrome，症状仍为选中英文没有图标。
- 检查时 GUI 显示正常输入页、没有缺少辅助功能的提示，页脚也未显示暂停。运行路径仍为本项目 `dist/HyperTranslate.app`，1.0.1 的签名未被重新打包改变。
- 在 Chrome 当前页面双击 `water` 后，辅助功能界面确认单词已被选中，但截图中未见图标；尚不能把原因唯一归为鼠标移动。
- 代码确定存在时序缺陷：等待 180 毫秒后才采样鼠标位置，随后要求鼠标在选区周围 30 点内。因此用户松开后移走鼠标，会丢弃已选文本。键盘选区也不应受鼠标远近限制。

### 修改

- 在鼠标松开或键盘选择触发时保存坐标、主屏坐标原点和来源进程；防抖后只读取这份快照。
- 鼠标选择继续过滤真正点击选区外的残留文本。键盘选择只从焦点元素读取，并优先按选区矩形定位。
- 监听启动前先移除旧监听，避免重复注册；权限准备页增加最近取词状态，不记录所选文本、网址或浏览历史。可区分监听启动失败、未授权、暂停以及来源应用未提供英文选区。
- 版本更新为 1.0.2（build 3）。

### 验证

- 新增 5 项取词回归测试：防抖期间移动鼠标、残留选区过滤、键盘选区定位、矩形缺失与副屏负坐标、取消防抖不再读取旧选区。
- 最终 24 项测试全部通过，Debug、Release 编译及正式包签名严格校验通过。此结果证明已覆盖的代码行为，不宣称所有 Chrome 页面或其他应用均已兼容。
- 1.0.2 首次启动实测显示未取得辅助功能授权，语言包已安装。用户重新添加并开启后，GUI 实机显示「已授权」，设置中版本为 1.0.2，暂停开关关闭。
- 重新授权后，自动化双击 Chrome 页面能确认 `water` 被选中，但应用最近取词状态仍为其他应用的读取记录，不能据此判断新版 Chrome 全局鼠标事件及取词成功或失败。已请求用户手动测试，并在失败时提供「取词状态」原文；Chrome 端到端验收尚待该结果。
